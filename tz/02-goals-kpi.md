# 2. Назначение системы, цели и KPI

Раздел 2 оригинала (п. 2.1–2.3).

## 2.1. Назначение системы

1. Цифровизация деятельности Агентства и организаций его системы.
2. Онлайн-мониторинг работ по выдаче разрешений.
3. Выдача физическим и юридическим лицам электронных разрешений: **выпас скота, сенокошение, размещение пчёл, рекреация, сбор дров/сучьев/хвороста, научные исследования**.
4. Ведение учёта пастбищных и прочих используемых земель **на основе GIS**.
5. Формирование базы данных по скоту, выпасаемому на пастбищных землях, и его численности, с интеграцией в другие государственные информационные системы.
6. Обеспечение отдельного функционального контура **«Цифровой надзор»** для органов прокуратуры, роли «Прокурор» и полных Read-Only возможностей контроля.

## 2.2. Цели создания

1. Прозрачная система выдачи разрешений на пользование землями лесного фонда, открытая для всех.
2. Онлайн-мониторинг работ организаций системы Агентства по выдаче разрешений.
3. Точная база данных по используемым землям, находящемуся на них скоту и нагрузке в условных головах.
4. **Автоматическое предложение только тех площадей, которые разрешены юридически и по GIS.**
5. Устранение бумажной волокиты, длительного ожидания и коррупционных проявлений.
6. Сокращение времени и расходов при ведении дел за счёт использования ИС.
7. Одинаковый результат госуслуги в каналах **my.gov.uz** и **ruxsatnoma-urmon.uz**.
8. Возможность инспектору проводить мониторинг на основе **QR, GPS, фото и электронного акта**.
9. Формирование единой информационной и интеграционной среды с платформой **Smart Forestry**.
10. Через интеграцию с «Raqamli nazorat» — регистрация системы/ресурса, верификация сотрудника прокуратуры и территориальный Read-Only контроль.

## 2.3. Целевые KPI

| Показатель | Цель | Способ измерения |
|---|---|---|
| Доля электронных заявок | ≥ 95 % | Поступившие через АТ / my.gov.uz по отношению ко всем заявкам |
| Автоматические проверки | ≥ 80 % | Доля проверок, проведённых без ручного запроса данных |
| Разрешения, связанные с GIS | 100 % | Наличие valid geometry и `contour_id` у активных разрешений |
| Ручная отметка «оплачено» | **0 %** | Отсутствие статуса `PAID` без подтверждения провайдера/банка |
| Доступность системы | ≥ 99,5 % в месяц | Мониторинг вне планового обслуживания |
| Выполнение SLA рассмотрения заявки | ≥ 98 % | Доля заявок, завершённых в 15-дневный срок |
| Повторные (дублирующие) активные заявки | **0** | Счётчик попыток, отклонённых constraint'ом СУБД |
| Охват «Цифрового надзора» | 100 % | Все юридически значимые операции (утверждение, подпись, оплата, изменение тарифа/нормы) попадают в надзорный поток |
| Задержка передачи риск-индикатора | ≤ 5 минут | С момента фиксации события до доставки в «Raqamli nazorat» |
| Ручные ответы на запрос прокурора | **0** | Доля сведений, запрошенных вне системы (письмом/на бумаге) |
| Операции записи под ролью «Прокурор» | **0 %** | Любая write-операция под ролью «Прокурор» в аудите |
| Удовлетворённость пользователей | ≥ 4,5 / 5 | Форма оценки на портале и в my.gov.uz |

## Что из KPI напрямую превращается в требования к коду

Четыре показателя — это не метрики, а инварианты, которые нужно заложить в архитектуру:

- **`PAID` без подтверждения провайдера = 0.** Статус `PAID` может ставить только обработчик подписанного webhook'а. Ручная установка — только через maker-checker с приложением банковского документа и автоматической генерацией `RI-01`.
- **Дубликаты = 0.** Требуется unique constraint на уровне СУБД по `applicant_id + contour_id + activity_type` с пересечением периодов (exclusion constraint по `tstzrange`).
- **GIS-связность = 100 %.** У каждого активного разрешения обязателен непустой валидный `contour_id` + geometry. Проверяется constraint'ом, а не кодом.
- **Write под ролью «Прокурор» = 0.** Read-Only на трёх уровнях (UI / API / СУБД), см. [15-risk-indicators.md](15-risk-indicators.md).
