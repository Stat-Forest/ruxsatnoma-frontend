### Ключевое наблюдение: это не одна система, а две

Модели содержат разделитель `client_type`:

```python
class ClientType(models.TextChoices):
    MOBILE = "Mobile", "Forest"      # мобильное приложение Forest
    WEB = "Web", "Ruxsatnoma"        # портал ruxsatnoma-urmon.uz
```

Приложения `forest`, `message`, `service`, `news`, `ecotourism` и половина `accounts` (Firebase-токены, push-уведомления, белые и чёрные списки телефонов, версии приложения) обслуживают **мобильное приложение Forest**, а не Ruxsatnoma. В коде они помечены комментариями `# FOREST MOBILE START` / `# FOREST MOBILE END`.

Собственно Ruxsatnoma — это `application` + `payment` + `idgovauth` + часть `accounts`, то есть примерно **4 500 строк из 10 000**.

## 3. Почему система медленная

Причины найдены в коде и конфигурации. **Ни одна из них не связана с монолитной архитектурой.**

### 3.1. Один воркер Gunicorn

`docker-compose.prod.yml`:

```yaml
command: gunicorn urmonrental.wsgi:application --bind 0.0.0.0:3636 --log-level=debug
```

Флаг `--workers` не задан. Значение по умолчанию — **1 воркер синхронного типа**. Это означает, что вся система обрабатывает **один HTTP-запрос за раз**. Второй пользователь ждёт, пока освободится единственный процесс.

ТЗ требует 1000 одновременных пользователей.

### 3.2. Отладочное логирование в продакшене

В той же команде — `--log-level=debug`. В `production.py` корневой логгер тоже на уровне `DEBUG`. Плюс собственный `LogMiddleware` пишет две строки в лог на каждый запрос, включая репрезентацию объекта `request`.

### 3.3. `inspect.stack()` в горячем пути

`apps/application/models.py`, метод `Application.save()`:

```python
if self.status != self.__original_status:
    import inspect
    for frame_record in inspect.stack():
        if frame_record[3] == 'get_response':
            request = frame_record[0].f_locals['request']
            break
```

`inspect.stack()` разворачивает **весь стек интерпретатора Python** с чтением исходников для контекста каждого кадра. Это одна из самых дорогих операций в стандартной библиотеке. Вызывается при каждой смене статуса заявки, при каждом создании заявки (в `post_save`) и дважды в `apps/payment/models.py`.

Всего 4 таких места.

### 3.4. Внешние вызовы внутри цикла запроса

Очереди задач нет вообще. Поэтому:

- SMS отправляется синхронно в `post_save` сигнале при создании заявки;
- SMS-код регистрации отправляется синхронно в `post_save` для `ActivationCode`;
- Firebase push рассылается синхронно в `post_save` для `Notification`, причём при типе `MULTIPLE` — **всем пользователям сразу**, в одном запросе;
- запросы в Telegram API — синхронно.

Всего **16 мест** с прямыми `requests.get`/`requests.post`. Если внешний сервис отвечает медленно, пользователь ждёт вместе с ним — а воркер, напомню, один.

### 3.5. Отсутствие индексов

Во всех моделях проекта — **один** `db_index=True` (на `User.username`). Ни составных индексов, ни `Meta.indexes`, ни `unique_together`. При этом выборки идут по `status`, `department`, `application_number`, `created_at`.

### 3.6. N+1 запросы

На 10 000 строк кода — **10** вызовов `select_related`/`prefetch_related`. Списки заявок с обращением к `user`, `department`, `contour`, `massive` и статусам гарантированно порождают N+1.

### 3.7. Отсутствие тестов

162 строки тестов на весь проект, из них 132 — заготовка в `apps/application/tests.py`.

## 6. Расхождения между действующей системой и новым ТЗ

Это находки, требующие решения Заказчика. Добавлены в [`../qa/questions-to-customer.md`](../qa/questions-to-customer.md).

### 6.1. Охота есть в системе, но её нет в новом ТЗ

```python
APPLICATION_TYPES = (
    ("pet_feeding", "Чорва молларини боқишга"),
    ("haymaking",   "Пичан ўришга"),
    ("hunting",     "Овчилик йўлланмаси"),      # ← охотничья путёвка
)
```

Есть и отдельная категория организации:

```python
DEPARTMENT_CATEGORY = (
    (1, "Ўрмон агентлиги"),
    (2, "Овчилик департаменти"),                # ← департамент охоты
)
```

Под охоту сделан отдельный механизм динамических полей формы (`ApplicationKey` / `ApplicationKeyValue`) с ценой на каждое поле — то есть охотничья путёвка тарифицируется по видам добычи.

Новое ТЗ перечисляет 6 видов деятельности, **охоты среди них нет**. Вопрос: она выводится из системы, остаётся как есть или должна войти в новую?

### 6.2. Два платежа вместо одного

Действующая система берёт деньги дважды:

```python
TYPE_TRANSACTIONS = (
    (2, "Ариза тўлови"),   # сбор за рассмотрение заявки
    (3, "Ижара тўлови"),   # плата за пользование
)
```

Заявка вообще не принимается к рассмотрению, пока не оплачен сбор — статус 1 «Тўлов қилинмаган» именно об этом.

Новое ТЗ знает только один платёж — 100 % предоплата по разрешению (ВМҚ 278-сон). Сбора за рассмотрение заявки в нём нет.

Вопрос: сбор за рассмотрение отменяется или сохраняется?

### 6.3. Внутренний кошелёк и токенизация карт

`apps/payment/` содержит `AccountBalance` (баланс пользователя), `AccountCard` (сохранённые карты Uzcard/Humo с токеном) и `BalanceTransaction` (движения по балансу). Нового ТЗ это не касается вовсе.

Вопрос: кошелёк переносится в новую систему или упраздняется?

### 6.4. Расчёт в целых числах

`calculate_animal_price` и `calculate_haymaking_price` приводят результат к `int()`, то есть отбрасывают дробную часть:

```python
haymaking_price = int(ha * (settings.haymaking_price * settings.bhm))
```

Новое ТЗ (п. 4.3.1) требует **decimal-арифметику с явной политикой округления**. При миграции суммы могут разойтись с историческими.

### 6.5. Мобильное приложение Forest

Половина кода обслуживает мобильное приложение Forest (новости, экотуризм, паспорта лесов, обращения граждан, push-уведомления). Новое ТЗ его не упоминает.

Вопрос: приложение остаётся на старой системе, переносится или закрывается? От этого зависит, что делать со старым монолитом после запуска новой системы.

## 7. Выводы

1. **Медленная работа вызвана конфигурацией и кодом, а не архитектурой.** Один воркер Gunicorn, отладочное логирование в проде, `inspect.stack()` в горячем пути, отсутствие индексов, N+1 и синхронные внешние вызовы без очереди. Ни одна из этих причин не устраняется разделением на микросервисы.

2. **Настоящая структурная проблема — два продукта в одной кодовой базе.** Ruxsatnoma и мобильное приложение Forest переплетены через общие модели `User`, `Region`, `Department` и через флаг `client_type`. Разделять надо по продуктам, а не по техническим слоям.

3. **Переиспользовать из кода почти нечего, кроме знаний.** Ценны: рабочие интеграции (OneID, E-IMZO, ИМУТ, Payme, Paynet, Eskiz), действующие тарифные коэффициенты в таблице `Settings`, набор статусов и структура справочников. Сам код на Django 3.0 с бизнес-логикой в сигналах переписывается целиком.

4. **Объём новой системы примерно в 5–10 раз больше старой.** Действующие 10 000 строк покрывают 2 сценария из 27, без GIS, без rule engine, без инспектора, без надзора, без отчётности.
