# Цифровой надзор и риск-индикаторы

Пункт 4.2.11 и приложение 6.2 оригинала.

## Правовое основание

Подсистема выполняет требование стратегии **«Цифровая прокуратура – 2030»**, утверждённой Указом **ПФ-204-сон** от 03.11.2025 (гл. 3, п. 5), о внедрении функции «цифрового надзора» в государственных информационных системах.

> Отдельно тот же Указ требует, чтобы ТЗ на создание и модернизацию ИС **проходили экспертизу на наличие функции «цифрового надзора»**. Настоящее ТЗ приведено в соответствие с этим требованием.

Подсистема состоит из **четырёх функциональных контуров**.

---

## 4.2.11.1. Контур входа и верификации

- Для сотрудников прокуратуры — **выделенная веб-страница через ИМУТ** (закрыта от публичного интернета, с IP allowlist).
- Вход через **ЭЦП E-IMZO или OneID**; **вход по паролю запрещён**.
- ЖШШИР отправляется в «Raqamli nazorat», запрашиваются статус сотрудника, должность, код территории и срок полномочий.
- При положительном ответе **автоматически присваиваются роль «Прокурор» и территориальная граница ABAC**; **ответ не кэшируется**, запрашивается заново при каждом входе.
- По истечении срока полномочий учётная запись **автоматически приостанавливается**.

---

## 4.2.11.2. Контур Read-Only витрины

Прокурор знакомится в режиме только просмотра со следующими данными:

| Категория данных | Видимое содержание |
|---|---|
| **Заявка** | Все реквизиты, история статусов, отметки SLA, причины отказа и правовые основания |
| **Расчёт** | `MaxSB`, `RemainingSB`, `UsedSB`, тариф, сумма, `rule_version` и input snapshot |
| **Разрешение** | Реквизиты, документ PDF/A, сведения о подписи и сертификате, статус QR |
| **Платёж** | Инвойс, транзакция, банковская выписка, распределение, расхождения reconciliation, refund |
| **GIS** | Геометрия контура/субконтура, версии, подтверждающие документы, пересечения |
| **Норма** | Норма пользования, геоботанический документ, период действия, ID подтверждающего документа |
| **Инспекция** | Акт, чек-лист, метаданные фото, GPS, статус нарушения |
| **Аудит и метаданные** | Кто, когда, с какого IP/устройства, на каком основании изменил |

**Возможности:** поиск (ЖШШИР/СТИР, номер разрешения, ID контура, территория, период, статус, сумма, ответственный сотрудник); многокритериальная фильтрация и сохраняемые профили фильтров; сравнительный и трендовый анализ; формирование отчётов и экспорт PDF/XLSX (**с watermark и ID пользователя**).

**Ограничения:** все операции записи закрыты на уровне приложения, API и СУБД; открыты только методы `GET`; объём экспорта ограничивается; персональные данные показываются в пределах необходимости, лишнее маскируется.

## 4.2.11.3. Контур риск-индикаторов

Система автоматически выявляет перечисленные ниже ситуации, **передаёт их в «Raqamli nazorat» не дожидаясь запроса прокурора** и отмечает на внутреннем dashboard.

Перечень из текста п. 4.2.11.3:

1. установка статуса `PAID` без подтверждения провайдера или банка;
2. выдача разрешения сверх нормы или лимита;
3. несколько активных разрешений на один контур в пересекающемся периоде;
4. нарушение срока SLA;
5. ретроактивное (за прошедший период) изменение тарифа или нормы;
6. попытка подписания отозванным или просроченным сертификатом;
7. попытка изменения или удаления журнала аудита;
8. необычно большое число утверждений одним сотрудником за короткое время;
9. пропуск заявки на основании неутверждённой нормы;
10. активация разрешения без оплаты;
11. необоснованный или отклоняющийся от формулы расчёт refund;
12. попытка доступа к данным вне территориальных полномочий.

## 4.2.11.4. Контур обмена и подотчётности

- Система регистрируется в «Raqamli nazorat» с **ID системы/ресурса**.
- Каждое юридически значимое событие (**утверждение, подпись, платёж, изменение тарифа/нормы, отказ, аннулирование**) передаётся как event.
- **Каждое действие прокурора по просмотру, поиску и экспорту также записывается в аудит и возвращается в надзорную систему — контроль двусторонний.**
- При обрыве связи данные не теряются благодаря outbox и retry; недоставленные сообщения попадают в DLQ, администратору отправляется предупреждение.

Технический контракт обмена (методы, mTLS, заголовки) — в [05-integrations.md](05-integrations.md).

## Что это означает для реализации

Собранные воедино требования по этой подсистеме:

| Требование | Уровень реализации |
|---|---|
| Read-Only для роли «Прокурор» | UI + API (только `GET`) + **отдельный пользователь СУБД `read_only` и view'ы** |
| Сетевая изоляция | Отдельный домен/поддомен, только ИМУТ, IP allowlist, закрыт от публичного интернета |
| Аутентификация | Только E-IMZO/OneID, пароль запрещён, TTL сессии ≤ 30 минут |
| Верификация | Живой запрос в «Raqamli nazorat» при **каждом** входе, **без кэширования** |
| Передача событий | Асинхронный push с outbox, retry, DLQ, `Idempotency-Key`, mTLS, ЭЦП сообщения |
| Задержка передачи | ≤ 5 минут для «немедленных» индикаторов |
| Аудит действий прокурора | Append-only, плюс обратная отправка в «Raqamli nazorat» |
| Экспорт | Лимит объёма, watermark, ID пользователя, запись в аудит и в надзорную систему |
| Восстановление подсистемы при сбое | 4 часа |
| Целевой KPI | 100 % охват юридически значимых операций; **0 % write-операций под ролью «Прокурор»** |
