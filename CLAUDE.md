# Ruxsatnoma — точка входа

Государственная система выдачи электронных разрешений на пользование землями лесного фонда Республики Узбекистан. Заказчик — Агентство по лесам, исполнитель — ГУ «Центр цифровизации лесного хозяйства».

**Прочитай это целиком, прежде чем что-либо делать.** Ниже — состояние проекта и куда смотреть. Не изучай ТЗ и код старой системы заново: они уже разобраны.

Этот репозиторий — рабочая база проекта. Соседние репозитории лежат рядом, на уровень выше: `../ruxsatnoma-core`, `../ruxsatnoma-integration`, `../ruxsatnoma-frontend`, `../ruxsatnoma-old`.

## Что за система

Выдача разрешений на 6 видов пользования лесным фондом: выпас скота, сенокошение, размещение пчелиных ульев, рекреация, сбор дров и хвороста, научные исследования.

12 подсистем, 27 сценариев, 12 внешних интеграций, 84 организации, до 1000 одновременных пользователей, не менее 30 000 разрешений в год.

Действующая платформа — Django-монолит 2021 года, покрывает 2 сценария из 27, без GIS и без расчёта норм. Переписывается с нуля.

## Архитектура

**Два бэкенд-сервиса и фронтенд.** Не четыре, как задумывалось изначально — обоснование в [`architecture/diagrams.md`](architecture/diagrams.md).

| Репозиторий | Что внутри |
|---|---|
| `../ruxsatnoma-core` | Модульный монолит: IAM, заявки и workflow, GIS, rule engine, разрешения, ЭЦП, платёжный домен, инспектор, отчёты, архив, аудит, витрина прокурора |
| `../ruxsatnoma-integration` | Адаптеры к 12 внешним системам, outbox, retry, DLQ, воркеры очередей, BFF my.gov.uz, обмен с «Raqamli nazorat» |
| `../ruxsatnoma-frontend` | Next.js: публичный портал (SSR), кабинеты, карта, PWA инспектора |
| `../ruxsatnoma-gis`, `../ruxsatnoma-payment` | Пустые, зарезервированы под будущее выделение модулей |
| `../ruxsatnoma-old` | Код действующей системы, **только справочник** — см. его `CLAUDE.md` |
| **этот репозиторий** | Вся документация |

Стек: **Python + FastAPI**, PostgreSQL 18 + PostGIS 3.6, SQLAlchemy 2.0 + GeoAlchemy2, Redis, RabbitMQ, MinIO, nginx, Next.js. Отдельного API Gateway нет — его роль выполняет nginx.

Инструменты: Ruff, mypy в строгом режиме, pytest с testcontainers, import-linter, pre-commit, bandit, pip-audit. Подробно — в [`architecture/engineering-standards.md`](architecture/engineering-standards.md).

## Решения, которые уже приняты — не пересматривай без запроса

1. **Два сервиса, не четыре.** Действующая система тормозит из-за конфигурации и кода, а не монолитности. Микросервисы этого не лечат.
2. **Прокурор — роль, а не сервис.** Требования ТЗ закрываются пулом соединений `read_only`, вторым vhost в nginx и middleware «только GET».
3. **Платежи — модуль в `core`,** адаптеры провайдеров (Payme, Click, Uzum, Paynet) — в `integration` за единым интерфейсом.
4. **GIS — модуль в `core`,** потому что проверка занятости синхронна при каждой подаче заявки и обязана уложиться в 5 секунд.
5. **Отдельного API Gateway нет** — nginx.
6. **Мобильное приложение Forest вне области работ.** Половина старого монолита обслуживает его — игнорируй.
7. **Язык — Python, фреймворк FastAPI.** Решено 8 августа 2026, закрывает вопрос Р4 к Заказчику.
8. **DDD применяется выборочно.** Берём единый язык, агрегаты, объекты-значения и доменные события. Не берём event sourcing, CQRS и лишние слои — обоснование в [`architecture/engineering-standards.md`](architecture/engineering-standards.md).

## Чего нельзя делать

- Писать код в `../ruxsatnoma-old` — это справочник.
- Считать деньги в `float` или `int`. Только `numeric(18,2)` — старая система теряла копейки на `int()`.
- Класть бизнес-логику в сигналы и в `save()` — так сделано в старой системе, и это одна из причин, почему она медленная.
- Ходить во внешние системы синхронно из цикла запроса. Для этого есть `integration` и очереди.
- Пересчитывать ранее выданные разрешения при изменении нормы. Они держатся за свой `rule_version` и `input_snapshot`.
- Тестировать на SQLite. Он не умеет ни PostGIS, ни exclusion constraints, ни RLS — то есть ровно то, на чём держатся инварианты. Только реальный PostgreSQL через testcontainers.
- Выставлять наружу объекты SQLAlchemy из публичного API модуля — иначе шов для выделения `geo` и `payment` зарастает в первый же месяц.
- Изобретать имена. Сущности называются так, как в едином языке — [`architecture/engineering-standards.md`](architecture/engineering-standards.md), раздел 2.
- **Писать в коде что-либо кроме английского.** Имена, комментарии, docstring-и, тексты исключений, сообщения коммитов, имена веток и миграций, ключи логов — только английский. Русский это язык документации и обсуждений, узбекский — язык ТЗ и интерфейса. Тексты для пользователя живут в `locales/`, а не в исходниках. Проверяется скриптом в CI.
- **Пушить, не проверив состояние PR текущей ветки.** См. раздел «Git» ниже.

## Git

**Перед каждым `git push` проверять, жив ли PR ветки.** Смерженный или закрытый PR новые коммиты не подхватывает: они остаются висеть в ветке, в `main` не попадают, и это обнаруживается через несколько часов работы поверх них.

```bash
gh pr list --head "$(git branch --show-current)" --state all --json number,state,mergedAt
```

| Что показало | Что делать |
|---|---|
| PR открыт | Пушить в ветку, PR обновится сам |
| PR смержен или закрыт | Ветку не трогать. Новая ветка от свежего `origin/main`, перенести коммиты, новый PR |
| PR нет | Пушить и создать PR |

Правило действует и для длинной сессии: PR мог быть смержен уже после того, как работа началась. Состояние проверяется непосредственно перед push, а не по памяти о начале сессии.

**Не коммитить в `main` напрямую** ни в одном из репозиториев. Исключение — самый первый коммит в пустом репозитории, где ветки `main` ещё не существует и PR не к чему прикрепить.

**Не добавлять в коммиты и PR упоминание ИИ** — ни `Co-Authored-By`, ни строку о генерации в теле PR.

## Разделение труда: что делает техлид, а что разработчики

Граница проходит здесь, и её нельзя размывать: разработчик, которому выдали готовую реализацию, теряет понимание своей же системы.

| Зона техлида | Зона разработчиков |
|---|---|
| Документация, ТЗ, архитектура | Модели SQLAlchemy |
| Схема БД **как описание** — ER-диаграммы, таблицы в MD | Миграции Alembic |
| Границы модулей, контракты между сервисами | Реализация модулей и адаптеров |
| Скелет **бэкенд-сервисов**: структура пакетов, конфигурация инструментов, CI | Бизнес-логика, эндпоинты, тесты |
| Дизайн-система, UI-кит, карта экранов, потоки | **Весь фронтенд целиком**, включая скелет проекта: Next.js, i18n, инструменты, компоненты, страницы |
| Окружение разработки, docker-compose | — |
| Ревью и приёмка результата | — |

> **Фронтенд-проект целиком за FE.** Скелет `ruxsatnoma-frontend` — структуру, i18n, инструменты и сборку — заводит фронтендер сам. От техлида он получает дизайн, а не заготовку кода. Для `core` и `integration` скелеты были сделаны техлидом до этого решения — переделывать их обратно смысла нет.

**Проверять гипотезу на живой базе техлиду можно и нужно** — например, соберётся ли exclusion constraint. Но проверка гипотезы заканчивается там, где начинается реализация: снял риск, записал результат в документацию, отдал разработчику.
