# Миграция данных

Требование владельца: **ни одна запись не теряется**. Схемы маппинга и фаз — [`diagrams.md`](diagrams.md), схемы 10 и 11. Здесь — правила, соответствия полей и порядок сверки.

Источник — база `db_urmonrental` действующей системы, PostgreSQL 12, Django 3.0. Разбор — [`../tz/20-legacy-code-audit.md`](../tz/20-legacy-code-audit.md).

---

## 1. Правила, действующие на всю миграцию

**Каждый скрипт идемпотентен.** Повторный запуск не создаёт дублей и не портит уже перенесённое. Проверяется по `legacy_id`.

**Каждая перенесённая строка хранит происхождение.** Поля `legacy_id bigint` и `legacy_table text` — чтобы в любой момент проследить строку до исходной базы и сверить.

**Суммы не пересчитываются.** Старая система считала через `int()` и отбрасывала копейки. Пересчёт по новым формулам даст другие числа, и бухгалтерия не сойдётся с историей. Переносим как есть, в `calculation.is_legacy` ставим `true`.

**Старая база после перехода — только на чтение.** Держится минимум 6 месяцев для сверки.

**Персональные данные.** Дамп содержит паспортные данные, ЖШШИР, телефоны. Порядок хранения и уничтожения рабочей копии согласуется отдельно — это часть вопроса **О2**.

## 3. Соответствие статусов

Десять статусов старой системы против четырнадцати новых.

| Старый | Новый | Комментарий |
|---|---|---|
| 1 — Тўлов қилинмаган | ⚠️ нет аналога | Сбор за рассмотрение заявки. Зависит от ответа **О10** |
| 2 — Янги | `SUBMITTED` | |
| 3 — Кўриб чиқилмоқда | `IN_REVIEW` | |
| 4 — Кўриб чиқилган | `APPROVED` | |
| 5 — Рухсатнома учун тўлов қилинган | `PAID` | |
| 6 — Рухсатнома берилган | `PERMIT_ISSUED` | Плюс создаётся `permit.permit` |
| 7 — Бекор қилинган | `CANCELLED` | |
| 8 — Рад этилган | `REJECTED` | Код `RJ-15` «прочее», исходной причины в старой системе нет |
| 9 — Ўчирилган | `ARCHIVED` | |
| 10 — Муддати ўтган | `EXPIRED_UNPAID` или `EXPIRED` | По контексту: истёк срок оплаты или срок разрешения |

**Статус 1 — открытый вопрос.** Если сбор за рассмотрение отменяется (ответ на **О10**), заявки в этом статусе переносятся как `DRAFT` или `CANCELLED` — решение за Заказчиком. Если сохраняется — в новую статус-машину придётся добавить состояние перед `SUBMITTED`.

**Статус 8 теряет причину отказа.** В старой системе она хранилась свободным текстом в `deadline_cause` или не хранилась вовсе. Классификатора `RJ-*` там нет. Переносим с `RJ-15` и исходным текстом в примечании.

| Старое поле | Новое | Преобразование |
|---|---|---|
| `application_number` | `app.application.number` | Как есть |

| `department_id` | `organization_id` | Через соответствие организаций |
| `type` | `activity_type` | `pet_feeding` → `GRAZING`, `haymaking` → `HAYMAKING`, `hunting` → **ждём О9** |
| `start_date`, `expire_date` | `period` | Сборка в `daterange` |
| `contour_id` | `contour_id` | Контур со статусом `Legacy` |
| `contour_info`, `massive_info`, `section_info`, `rotation_info` | Примечание | **Свободный текст**, структуры не имеет |

## 5. Контуры без геометрии

Главная сложность миграции.

В старой системе модель `Contour` — это `department`, `name`, `status`. **Геометрии нет вообще.** Значит все перенесённые контуры не могут участвовать в проверке занятости.

Решение:

```
geo.contour
    status      = 'LEGACY'
    geometry    = NULL
    legacy_id   = <id из старой базы>
```

| Что можно | Что нельзя |
|---|---|
| Привязывать к ним исторические заявки и разрешения | Подавать новые заявки |
| Показывать в архиве и отчётах | Считать занятость и лимит |
| Искать по названию | Отображать на карте |

Когда GIS-подразделение даст настоящие полигоны (вопрос **Б1**), контуры сопоставляются с `LEGACY`-записями по названию и лесхозу, геометрия дописывается, статус меняется на `Draft` и дальше идёт по обычному жизненному циклу.

Сопоставление ручное или полуавтоматическое — названия в старой базе неформализованы.

## 6. Тарифы

Таблица `application_settings` — **одна строка без истории**. Новая схема требует версионирования.

```
rules.tariff
    effective_from = дата запуска старой системы
    effective_to   = дата перехода на новую
    rule_version   = 'legacy-2021'
```

Все коэффициенты переносятся как множители БҲМ — это следует из `help_text` старой модели.

| Старое поле | Что означает |
|---|---|
| `bhm` | Базовая расчётная величина |
| `legal_application_fee`, `unlegal_application_fee` | Сбор за рассмотрение, юр. и физ. лицо |
| `big_animals_price` | КРС, лошади, ослы, верблюды — взрослые |
| `middle_animals_price` | Те же виды до 2 лет |
| `big_sheeps_goats_price` | Овцы и козы старше 6 месяцев |
| `middle_sheeps_goats_price` | Овцы и козы до 6 месяцев |
| `haymaking_price` | Сенокошение за гектар |

Чего в старой системе нет и что придётся получать от Заказчика: коэффициенты условных голов (**Н1**), календарь сезонов и ротации (**Н3**), нормы пользования (**Б2**). Расчёта норм в старой системе не было вовсе.

## 7. Пользователи

Переносятся: ЖШШИР, СТИР, паспорт, Ф. И. О., телефон, адрес, организация, тип лица.

**Пароли не переносятся.** Причины: хеши Django несовместимы с Argon2id, а по новой модели заявителям пароль вообще не выдаётся — только OneID или E-IMZO. Внутренним сотрудникам администратор выдаёт одноразовый пароль со сменой при первом входе.

Пользователи с `client_type = 'Mobile'` — из мобильного приложения Forest, **не переносятся**. Если у пользователя оба типа, переносится веб-часть.

## 8. Фазы перехода

Восемь фаз из схемы 11. Первые четыре выполняются заранее и не мешают работе действующей системы.

| Фаза | Что | Когда |
|---|---|---|
| **0. Инвентаризация** | Дамп, объёмы, битые записи, выгрузка тарифов | Задачи 0.2–0.5 |
| **1. Справочники** | 90 организаций, регионы, праздники | Заранее |
| **2. Контуры** | Как `LEGACY` без геометрии | Заранее |
| **3. Пользователи** | Без паролей | Заранее |
| **4. История** | Завершённые заявки, разрешения, счета, транзакции | Заранее |
| **5. Активные разрешения** | Действующие на момент перехода | **В окно перехода** |
| **6. Сверка** | Построчное сравнение количеств и сумм | В окно перехода |
| **7. Переключение** | Старая система в режим чтения, трафик на новую | В окно перехода |
| **8. Параллельная работа** | Старая база доступна для сверки | 6 месяцев |

**Фаза 5 — самая ответственная.** Действующие на момент перехода разрешения должны заработать сразу: проверка по QR, доступность инспектору, отображение в кабинете заявителя. Если человек с действующим разрешением не сможет его подтвердить инспектору на следующий день после перехода — это провал перехода независимо от остального.

## 9. Сверка

Без успешной сверки переключение не выполняется.

### Что сравнивается

| Проверка | Критерий |
|---|---|
| Число заявок по статусам | Совпадает построчно |
| Число разрешений | Совпадает |
| Число действующих разрешений | Совпадает |
| Сумма всех платежей | Совпадает **до копейки** |
| Число пользователей | Совпадает за вычетом только мобильных |
| Число организаций | Совпадает |
| Каждая заявка имеет `legacy_id` | Осиротевших нет |
| Обратная проверка: каждая исходная строка нашлась | Потерянных нет |

### Отчёт о расхождениях

Формируется автоматически, содержит: тип расхождения, идентификатор в старой базе, что ожидалось, что получилось. Отчёт **принимается бухгалтерией** — это отдельная задача 7.7, а не техническая формальность.

При расхождениях — разбор, исправление скрипта, повторный прогон. Идемпотентность позволяет прогонять сколько нужно.

## 10. Откат

Если после переключения обнаружится критическая проблема:

1. Трафик возвращается на старую систему — она в режиме чтения, снимаем ограничение
2. Новая система останавливается
3. Данные, введённые в новую систему после переключения, выгружаются и переносятся в старую вручную

Окно, в течение которого откат возможен без потерь, — **первые сутки**. Дальше объём новых данных делает откат дороже, чем починку.

Поэтому переключение планируется на начало недели, а не на пятницу.
