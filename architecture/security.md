# Модель безопасности

Требования разбросаны по ТЗ: аутентификация в п. 4.1.6, права в приложении 4, прокурорский контур в приложении 6, аудит в п. 4.2.4, защита данных в п. 4.1.6.3. Здесь они собраны в одну картину.

Разбор требований — [`../tz/12-nfr.md`](../tz/12-nfr.md), раздел 4.1.6. Права ролей — [`../tz/08-roles-permissions.md`](../tz/08-roles-permissions.md).

## 1. Аутентификация

Три способа входа, разные для разных ролей.

| Способ | Кому | Ограничения |
|---|---|---|
| **OneID** | Всем | Основной способ по ТЗ |
| **E-IMZO** | Всем | Обязателен для подписания документов |
| **Логин и пароль** | Только внутренним сотрудникам | **Обязательна MFA** |

**Заявителям пароль не выдаётся** — только OneID или E-IMZO. Это снимает целый класс проблем: восстановление, утечки, слабые пароли у десяти тысяч человек.

**Прокурору пароль запрещён прямым требованием ТЗ.** Только E-IMZO или OneID.

### Требования к паролю

Из п. 4.1.6.3: заглавные и строчные буквы, цифры, символы пунктуации, не менее 8 символов. Хранение — **Argon2id**. Пароль **никогда не отправляется по SMS** (п. 4.1.6).

Число попыток входа ограничено — 5, затем временная блокировка учётной записи и предупреждение администратору. Это `ERR-AUTH-003` и `429`.

### Сессии

| Роль | Время жизни | Обновление |
|---|---|---|
| Заявитель, сотрудник, руководитель | 8 часов | По refresh-токену |
| Администратор | 4 часа | По refresh-токену |
| **Прокурор** | **30 минут** | **Нет — только повторный вход с новой верификацией** |

Неактивность — автоматическая блокировка сессии с требованием повторного входа (п. 4.1.6.3). Сессии в Redis, инвалидация мгновенная при снятии роли.

## 2. Авторизация: RBAC плюс ABAC

Два уровня, оба обязательны.

**RBAC** отвечает на вопрос «что за действие»: может ли роль утверждать заявки, подписывать разрешения, менять норму. Матрица — приложение 4 ТЗ, 16 объектов на 10 ролей.

**ABAC** отвечает на вопрос «над какими данными»: только своя организация, только своя территория. Без него сотрудник Самаркандского лесхоза увидел бы заявки Ферганского.

### Атрибуты, по которым ограничивается доступ

| Атрибут | Источник | Где применяется |
|---|---|---|
| `organization_id` | Учётная запись | Сотрудник видит только свою организацию |
| `territory_code` | Учётная запись, для прокурора — ответ «Raqamli nazorat» | Территориальная граница |
| `territory_scope` | То же | `DISTRICT`, `REGION`, `REPUBLIC` |
| `activity_type` | Права роли | Специалист по нормам может отвечать за часть видов |
| `owner_id` | Объект | Заявитель видит только свои заявки |

### Три места проверки

Проверка дублируется намеренно — каждый уровень ловит то, что пропустил предыдущий.

| Уровень | Что проверяет | Что ловит |
|---|---|---|
| **Интерфейс** | Показывать ли элемент | Требование п. 4.1.7: кнопки без права не показываются |
| **API** | Роль и атрибуты в middleware | Прямой вызов эндпоинта в обход интерфейса |
| **СУБД** | RLS и права роли | Ошибку в коде приложения |

Третий уровень — не паранойя. Он существует потому, что первые два пишем мы, и мы ошибаемся.

## 3. Прокурорский контур

Отдельный раздел, потому что требования жёстче, чем ко всей остальной системе.

### Сетевой периметр

- Отдельный домен или поддомен
- Доступ **только через ИМУТ**, из публичного интернета закрыт
- IP allowlist на nginx
- Отдельный `server`-блок, не делит конфигурацию с публичным

### Верификация при каждом входе

```
E-IMZO или OneID → ЖШШИР → POST /verify-officer в «Raqamli nazorat»
    → должность, код территории, срок полномочий
    → присвоение роли и границы ABAC
```

**Ответ запрещено кэшировать.** Ни в Redis, ни в памяти процесса. Уволили прокурора — доступ пропадает в тот же день без участия администратора.

При недоступности «Raqamli nazorat» — `ERR-AUTH-005` и отказ во входе. Доступ не выдаётся «на всякий случай».

### Read-Only на трёх уровнях

Дословное требование приложения 6 ТЗ:

| Уровень | Как реализовано |
|---|---|
| **Интерфейс** | Изменяющие элементы отсутствуют в разметке, а не скрыты стилями |
| **API** | Открыты только `GET`; write-эндпоинты закрыты для роли в middleware |
| **СУБД** | Отдельный пользователь `oversight_ro`, отдельный пул соединений, `SELECT` без `INSERT`, `UPDATE`, `DELETE` |

Плюс RLS-политики по территории — см. [`database.md`](database.md), раздел 3.

Попытка записи возвращает `403` и `ERR-ACL-003`, пишется в аудит с критическим уровнем и порождает `RI-12`.

### Минимизация и контроль выгрузки

- Персональные данные показываются в пределах необходимости, лишнее маскируется
- Экспорт ограничен по объёму (вопрос **П10**)
- В документ проставляются watermark и ID пользователя
- Каждый просмотр, поиск и экспорт пишется в аудит и **возвращается в «Raqamli nazorat»** — контроль двусторонний

## 4. Защита данных

### При передаче

| Канал | Защита |
|---|---|
| Браузер и API | TLS 1.2 и выше (п. 4.1.6) |
| Между сервисами | mTLS |
| «Raqamli nazorat» | mTLS плюс подпись сообщения ЭЦП, только через ИМУТ |
| Платёжные провайдеры | HTTPS плюс подпись webhook |
| Кадастр, Ветеринария | По регламенту межведомственной интеграции |

### При хранении

| Что | Как |
|---|---|
| Пароли | Argon2id |
| Персональные данные в БД | Шифрование, требование п. 4.1.6 |
| Файлы в MinIO | Шифрование, checksum, versioning |
| Резервные копии | Шифрование, отдельное хранилище |
| Секреты приложения | Хранилище секретов, в БД только ссылка |

Учитываются государственные стандарты **O'z DSt 1105:2009** и **O'z DSt 1106:2009** (п. 4.1.6), а при обработке информации ограниченного пользования — **O'zDSt 2814:2014**.

### Что не попадает в логи

Персональные данные, пароли, токены, содержимое ЭЦП, номера карт. В логах остаются `correlation_id`, `user_id` и идентификаторы объектов — по ним всё восстанавливается, не раскрывая данные.

## 5. Аудит

Отдельная опора всей модели: если что-то пошло не так, аудит — единственный источник правды.

### Что фиксируется

Все действия с указанием **кто, когда, с какого IP, с какого устройства, на каком основании**. Плюс отдельные журналы: события информационной безопасности, резервное копирование, интеграционные сообщения, действия прокурора.

### Три свойства, которые нельзя нарушить

1. **Append-only.** `UPDATE` и `DELETE` отозваны на уровне СУБД, плюс триггер, поднимающий исключение. Администратор тоже не может.
2. **В одной транзакции с действием.** Требование п. 4.2.4: если действие откатилось, запись аудита откатывается вместе с ним. Не «сначала действие, потом лог».
3. **Хранение не менее 3 лет.** Партиционирование по месяцам, 36 активных секций.

### Попытка изменить аудит

Порождает `RI-06` **критического** уровня с немедленным оповещением SOC. Это единственный индикатор такого уровня наравне с `RI-10`.

## 6. Электронная подпись

По законам «Об электронной цифровой подписи» и «Об электронном документообороте», ключи ГНК по **ВМҚ 679-сон**, алгоритм по **O'z DSt 1092:2009**.

### Что проверяется при каждой подписи

1. Отсутствие ошибок подписания в документе
2. Подлинность права владения ЭЦП
3. Срок действия сертификата открытого ключа
4. **Статус сертификата в CRL и OCSP**: действует, приостановлен, отозван

Хранится подпись с **timestamp и hash**. Подписанный документ — immutable snapshot, изменению не подлежит.

Попытка подписать отозванным или просроченным сертификатом порождает `RI-05`.

### Разделение ответственности

Проверка подписи — stateless-операция в `integration` (внешний вызов к CRL и OCSP). Хранение сущности `signature` и политика «кто что подписывает» — в `core`. Обоснование — [`contracts.md`](contracts.md).

## 8. Управление правами

### Ежемесячный пересмотр

Прямое требование п. 4.1.6 и 4.2.2. Реализуется регламентным заданием `core-worker`: раз в месяц формируется список пользователей с их правами, администратор подтверждает или снимает. Результат пишется в журнал.

### Снятие прав

| Событие | Что происходит |
|---|---|
| Увольнение или смена должности | Права снимаются администратором, сессии инвалидируются |
| Истечение полномочий прокурора | **Автоматически** по данным «Raqamli nazorat» |
| Истечение доверенности представителя | Автоматически по сроку |
| Удаление пользователя | Блокируется, если есть незавершённые дела |

### Принцип наименьших привилегий

Роль получает ровно те функции, которые нужны. Администратор видит список **нераспределённых функций системы** — индикатор того, что какая-то возможность не покрыта ни одной ролью (п. 4.2.1.2).

## 9. Что делать при инциденте

| Инцидент | Реакция |
|---|---|
| Попытка изменить аудит | `RI-06`, оповещение SOC, блокировка операции |
| Разрешение активировано без оплаты | `RI-10`, оповещение, блокировка |
| Доступ вне территории | `RI-12`, `403`, запись в аудит |
| Подпись отозванным сертификатом | `RI-05`, отказ |
| Превышение попыток входа | Блокировка учётной записи, оповещение администратора |
| Недоступность «Raqamli nazorat» | Отказ во входе прокурору, события копятся в outbox |
| Компрометация секрета | Ротация в хранилище, инвалидация всех сессий |

Журнал событий информационной безопасности ведётся отдельно, с автоматическим оповещением SOC и дежурного администратора (п. 4.1.6).

## 10. Что проверяется тестами

Не «есть ли безопасность», а конкретные утверждения:

| Тест | Что доказывает |
|---|---|
| Под ролью `Прокурор` любой `POST`, `PUT`, `DELETE` даёт `403` | Read-Only на уровне API |
| Под пользователем `oversight_ro` любой `INSERT` падает с отказом прав | Read-Only на уровне СУБД |
| `UPDATE` и `DELETE` на `audit_log` падают | Append-only |
| Прокурор чужой территории не видит записей | RLS работает |
| Сотрудник чужой организации получает `403` | ABAC работает |
| Пароль не появляется в логах и в ответах API | Защита данных |
| Повторный webhook не создаёт вторую транзакцию | Идемпотентность |
| Вход после 5 неудачных попыток блокируется | Защита от подбора |

Все — интеграционные, на реальном PostgreSQL. См. [`engineering-standards.md`](engineering-standards.md), раздел 5.
