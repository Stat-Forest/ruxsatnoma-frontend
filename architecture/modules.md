# Границы модулей внутри `core`

`core` — модульный монолит. Работает как один процесс, но внутри разделён так, чтобы трое разработчиков не мешали друг другу, а `geo` и `payment` при необходимости выделялись в отдельные сервисы без переписывания.

Язык — **Python**, фреймворк — **FastAPI**. Инженерные стандарты, стек и правила тестирования — в [`engineering-standards.md`](engineering-standards.md).

## Главный принцип

**Пакет = схема базы данных.** Одиннадцать доменных пакетов, три общих. Разделение то же самое, что в [`database.md`](database.md) — это не совпадение, а требование: если модуль и схема не совпадают, границу невозможно проверить.

```
core/
├── api/                      REST-контроллеры, middleware, обработка ошибок
│   ├── middleware/           JWT, RBAC + ABAC, Correlation-Id, пул read_only
│   ├── errors.py             коды ERR-* из приложения 8 ТЗ
│   └── routes/               по одному файлу на модуль
│
├── modules/
│   ├── iam/                  схема iam       — пользователи, роли, организации, заявители
│   ├── geo/                  схема geo       — контуры, слои, занятость, тайлы
│   ├── rules/                схема rules     — нормы, тарифы, расчёт
│   ├── application/          схема app       — заявка, workflow, SLA
│   ├── permit/               схема permit    — разрешение, шаблоны, QR
│   ├── signature/            схема permit    — хранение подписей
│   ├── payment/              схема pay       — инвойс, сверка, распределение, возврат
│   ├── inspection/           схема insp      — акты, нарушения, медиа
│   ├── reporting/            схема rep       — отчёты, dashboard
│   ├── archive/              схема arch      — архив, лесной билет
│   └── prosecutor/           витрина и детекторы риск-индикаторов
│
├── shared/
│   ├── audit/                append-only журнал
│   ├── outbox/               исходящие события
│   └── classifiers/          схема nsi — справочники
│
└── worker/                   регламентные задания core-worker
```

## Устройство пакета

Каждый доменный пакет устроен одинаково:

```
modules/application/
├── __init__.py               ПУБЛИЧНЫЙ API — единственное, что видно снаружи
├── models.py                 таблицы схемы app
├── service.py                бизнес-логика
├── repository.py             запросы к схеме app
├── state_machine.py          переходы статусов
└── schemas.py                типы запросов и ответов
```

Снаружи виден **только `__init__.py`**. Всё остальное — внутреннее устройство модуля, которое можно менять без согласования.

## Три правила

### 1. Модуль работает только со своей схемой БД

Обращение к чужой таблице запрещено, **даже на чтение**. Нужны данные соседа — вызываешь его публичный API.

```python
# BAD: reaching into another module's schema
rows = db.execute("SELECT * FROM geo.contour WHERE id = :id", {"id": contour_id})

# GOOD: go through the module public API
from core.modules import geo
contour = geo.get_contour(contour_id)
```

Причина не в эстетике. Прямой запрос к чужой таблице привязывает твой код к её структуре, и владелец схемы больше не может её менять. Через полгода схему боятся трогать, и модульность заканчивается.

### 2. Модули общаются только через публичный API

Импортировать можно `core.modules.geo`, но не `core.modules.geo.repository`.

```python
# BAD: importing module internals
from core.modules.geo.repository import ContourRepository

# GOOD: only the package is public
from core.modules import geo
```

### 3. `shared` доступен всем и не зависит ни от кого

`audit`, `outbox` и `classifiers` импортирует кто угодно. Сами они **не импортируют ни один доменный модуль** — иначе получится цикл, и выделить что-либо станет невозможно.

Три наблюдения по матрице:

- **`geo`, `iam`, `archive` не зависят ни от кого.** Это листья графа — их можно писать первыми и параллельно всему остальному.
- **`prosecutor` читает всех, его не читает никто.** Он не участвует в бизнес-процессе, только смотрит. Именно поэтому его легко ограничить одним пулом соединений `read_only`.
- **Циклов нет.** Проверять при каждом изменении матрицы: цикл означает, что границу провели неправильно.

## Швы для будущего выделения

`geo` и `payment` помечены как кандидаты в отдельные сервисы. Для них правила строже:

| Обычный модуль | `geo` и `payment` |
|---|---|
| Публичный API — питоновский вызов | Публичный API должен выглядеть как сетевой: принимает и возвращает простые типы, никаких ORM-объектов наружу |
| Может участвовать в общей транзакции | Не рассчитывает на общую транзакцию с вызывающим — иначе при выделении сломается |
| Может кидать доменные исключения | Возвращает результат с кодом ошибки, как это делал бы HTTP-ответ |

Если соблюдать это с самого начала, выделение сводится к замене вызова функции на HTTP-клиент.

**Важное исключение.** Проверка занятости контура (`geo`) и создание заявки (`application`) обязаны быть в одной транзакции — иначе две заявки одновременно пройдут проверку. Это единственное место, где шов сознательно нарушен. Записано здесь явно, чтобы при выделении `geo` в сервис про это не забыли: тогда потребуется распределённая блокировка вместо `pg_advisory_xact_lock`.

## Автоматическая проверка

Правила, которые держатся на дисциплине, ломаются на третьей неделе. Нужен линтер импортов в CI.

Для Python это `import-linter` с описанием слоёв:

```ini
[importlinter]
root_package = core

[importlinter:contract:layers]
name = Layers
type = layers
layers =
    core.api
    core.modules
    core.shared

[importlinter:contract:private]
name = Module internals stay private
type = forbidden
source_modules = core.modules
forbidden_modules =
    core.modules.*.repository
    core.modules.*.models
```

Для других языков — свой инструмент, принцип тот же. Проверка обязательна перед слиянием в `main`.

## Владельцы пакетов

Владелец ревьюит все изменения в своих пакетах.

| Пакет | Владелец |
|---|---|
| `application`, `permit`, `inspection`, `archive` | Backend 1 |
| `geo`, `rules`, `reporting` | Backend 2 |
| `payment` | Backend 3 (домен), адаптеры провайдеров — в `integration` |
| `api`, `shared`, `iam`, `prosecutor`, `worker` | Технический лидер |

## Что делать при спорной границе

Если непонятно, в какой пакет положить код — задать два вопроса:

1. **В чью схему БД он пишет?** Туда и класть.
2. **Если ни в чью — кто владелец правила, которое он реализует?**

Если код нужен двоим и пишет в обе схемы — это признак, что задача разбита неправильно. Разделить на две части, каждая в своём пакете, и связать через публичный API.
