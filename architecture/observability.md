# Наблюдаемость

ТЗ требует диагностику (п. 4.1.1.5), мониторинг интеграций (п. 4.2.9), контроль SLA и показатели доступности ≥ 99,7 %. Здесь — как это устроено.

Отдельная причина, по которой раздел важен: действующая система пишет отладочный лог в проде и не имеет ни метрик, ни трассировки. Разобраться, почему запрос выполнялся девять секунд, там невозможно.

---

## 1. Три опоры

| Опора | Отвечает на вопрос | Инструмент |
|---|---|---|
| **Логи** | Что произошло с конкретным запросом | structlog, JSON |
| **Метрики** | Что происходит с системой в целом | Prometheus |
| **Трассировка** | Где именно ушло время | OpenTelemetry |

Плюс четвёртое, специфичное для этого проекта: **аудит**. Он не про наблюдаемость, а про юридическую значимость, и живёт отдельно — см. [`security.md`](security.md), раздел 5. Смешивать их нельзя: аудит нельзя удалять три года, логи ротируются через 30 дней.

---

## 2. Логи

### Формат

JSON, английские ключи, одна строка на событие.

```json
{
  "timestamp": "2026-09-15T10:30:00.123+05:00",
  "level": "info",
  "logger": "core.modules.application.service",
  "event": "application_submitted",
  "correlation_id": "018f2c5a-...",
  "user_id": "018f2e1b-...",
  "role": "APPLICANT",
  "territory_code": "1027",
  "object_type": "application",
  "object_id": "018f2f3c-...",
  "duration_ms": 342
}
```

`correlation_id` генерируется в nginx как `$request_id` и проходит через всю цепочку: `core` → `integration` → внешняя система → очередь → воркер. По одному идентификатору собирается вся история действия.

### Уровни

| Уровень | Когда | В проде |
|---|---|---|
| `debug` | Отладка | **Выключен** |
| `info` | Бизнес-события: заявка подана, платёж подтверждён | Включён |
| `warning` | Деградация: внешний сервис не ответил, сработал retry | Включён |
| `error` | Ошибка, требующая внимания | Включён |
| `critical` | `RI-06`, `RI-10`, отказ БД | Включён, плюс оповещение |

В действующей системе уровень `DEBUG` стоит и в команде запуска, и в настройках. У нас `debug` в проде не включается никогда — это отдельный пункт чек-листа развёртывания.

### Чего в логах нет

Персональные данные, пароли, токены, содержимое ЭЦП, номера карт, тела запросов с личными данными. Остаются идентификаторы — по ним всё восстанавливается через аудит, где данные хранятся законно.

### Хранение

Ротация по размеру и времени, 30 дней. Централизованный сбор — Loki или ELK, по возможностям ЦОД (вопрос **О1**).

## 3. Метрики

### Технические

| Метрика | Тип | Зачем |
|---|---|---|
| `http_request_duration_seconds` | histogram | **p95 ≤ 500 мс** — требование п. 4.1.4 |
| `http_requests_total` | counter | По маршруту, методу, коду ответа |
| `db_query_duration_seconds` | histogram | Медленные запросы |
| `db_connections_active` | gauge | Исчерпание пула |
| `queue_depth` | gauge | По каждой очереди |
| `dlq_size` | gauge | **Больше нуля — уже проблема** |
| `outbox_pending_age_seconds` | gauge | Задержка доставки событий |
| `external_call_duration_seconds` | histogram | По каждой из 12 систем |
| `circuit_breaker_state` | gauge | Открыт или закрыт, по системам |

### Доменные

Их обычно забывают, а они важнее технических: показывают, что система делает то, ради чего создана.

| Метрика | Зачем |
|---|---|
| `applications_submitted_total` | По виду деятельности, каналу, территории |
| `applications_by_status` | Сколько зависло в каждом статусе |
| `sla_deadline_approaching` | Заявки, у которых срок близко |
| `sla_violations_total` | **`RI-07`** |
| `permits_issued_total` | Против годового плана в 30 000 |
| `limit_check_duration_seconds` | **Требование ≤ 5 секунд** |
| `payment_confirmations_total` | По провайдерам |
| `payments_unreconciled` | Несверенные транзакции |
| `manual_paid_total` | **Должно быть 0** — KPI ТЗ |
| `risk_indicators_total` | По кодам `RI-01`…`RI-15` |
| `oversight_events_delivered` | Доставка в «Raqamli nazorat» |
| `prosecutor_write_attempts_total` | **Должно быть 0** — KPI ТЗ |

Три метрики со значением «должно быть ноль» — `manual_paid_total`, `prosecutor_write_attempts_total` и `dlq_size`. Любое отклонение от нуля — повод для оповещения, а не для наблюдения.

## 4. Трассировка

OpenTelemetry, спаны по всей цепочке.

Ключевой путь для трассировки — подача заявки. Требование ≤ 5 секунд на проверку лимита, и надо видеть, где именно уходит время:

```
POST /api/v1/applications/check          [850 ms]
├── auth.verify_jwt                       [ 12 ms]
├── geo.validate_geometry                 [ 45 ms]
│   └── db: ST_IsValid, ST_Within         [ 38 ms]
├── geo.get_available_area                [420 ms]
│   └── db: ST_Union over occupancy       [410 ms]   ← узкое место
├── rules.calculate_limit                 [180 ms]
│   ├── db: find published norm           [ 15 ms]
│   └── db: sum active permits sb         [160 ms]
└── rules.calculate_amount                [ 25 ms]
```

Без трассировки на вопрос «почему проверка идёт 5 секунд» отвечают гаданием. С ней — видно, что дело в объединении геометрий, и понятно, что чинить.

Трассируются: HTTP-запросы, запросы к БД, вызовы во внешние системы, публикация и обработка событий.

## 5. Проверки состояния

Три эндпоинта, разные по назначению. Их часто путают и делают один.

| Эндпоинт | Что проверяет | Кто вызывает |
|---|---|---|
| `GET /health/live` | Процесс жив | Оркестратор, для перезапуска |
| `GET /health/ready` | Готов принимать трафик: БД, Redis, брокер отвечают | Балансировщик |
| `GET /health/startup` | Миграции применены, кэши прогреты | Оркестратор, при запуске |

```json
GET /health/ready
{
  "status": "degraded",
  "checks": {
    "database": { "status": "ok", "latency_ms": 3 },
    "redis": { "status": "ok", "latency_ms": 1 },
    "rabbitmq": { "status": "ok", "latency_ms": 5 },
    "oneid": { "status": "degraded", "circuit": "open", "since": "2026-09-15T10:12:00+05:00" }
  }
}
```

`degraded` — не `unhealthy`. Внешний сервис недоступен, система работает в ограниченном режиме (п. 4.1.1.3). Трафик снимать не нужно.

## 6. Диагностика по ТЗ

Отдельное требование п. 4.1.1.5: диагностика программных и технических средств специальными программами-тестами в технологическом режиме.

| Что проверяет | Как |
|---|---|
| Физическая целостность ПО | Контрольные суммы образов и файлов при запуске |
| Логическая целостность ПО | Самопроверка при старте: миграции применены, схема соответствует ожидаемой, обязательные классификаторы заполнены |
| Работа на тестовых примерах | Набор синтетических сценариев, прогоняемых на `stage` перед выкатом |

Регистрация всех диагностических сообщений и формирование уведомлений о возможных значимых событиях — тоже требование п. 4.1.1.5.

## 7. Мониторинг интеграций

Требование п. 4.2.9 и сценария С26: состояние интеграции отображается на dashboard.

| Показатель | По каждой из 12 систем |
|---|---|
| Число запросов | За период |
| Доля ошибок | Процент |
| Среднее время ответа | И p95 |
| Состояние circuit breaker | Открыт или закрыт |
| Объём DLQ | Число сообщений |
| Возраст старейшего сообщения в outbox | Секунды |

Отдельно — **срок действия сертификатов**. При приближении к истечению интеграция останавливается и администратору отправляется предупреждение (сценарий С26, п. 26.1). Проверка ежедневная, оповещение за 30 дней.

## 8. Оповещения

Разделены по срочности. Правило: если оповещение можно посмотреть утром, оно не должно будить ночью.

### Критические — немедленно, в любое время

| Условие | Почему |
|---|---|
| `RI-06` — попытка изменить аудит | Критический уровень по ТЗ, оповещение SOC |
| `RI-10` — разрешение без оплаты | Критический уровень по ТЗ |
| Аудит не пишется | Восстановление 1 час по ТЗ |
| БД недоступна | Система стоит |
| `prosecutor_write_attempts_total` больше 0 | KPI нарушен |
| Доступность ниже 99,7 % за сутки | Нарушение SLA перед Заказчиком |

### Срочные — в рабочее время

Circuit breaker открыт дольше 15 минут, `dlq_size` больше 0, задержка доставки в «Raqamli nazorat» больше 5 минут, p95 выше 500 мс дольше 10 минут, сертификат истекает через 30 дней, резервное копирование не выполнилось.

### Сводки — ежедневно

`RI-07`, `RI-09`, `RI-15` — по ТЗ это ежедневная сводка, а не немедленное оповещение. Плюс несверенные платежи, заявки с приближающимся SLA, ошибки интеграций за сутки.

## 9. Панели мониторинга

| Панель | Для кого |
|---|---|
| **Техническая** | Дежурный администратор: доступность, p95, ошибки, очереди, БД |
| **Интеграции** | Администратор: 12 систем, circuit breakers, DLQ, сертификаты |
| **Бизнес** | Руководство: заявки, разрешения, платежи, SLA — это dashboard из подсистемы №7, часть продукта |
| **Надзор** | Риск-индикаторы, доставка в «Raqamli nazorat» |

Первые две — служебные, на Grafana. Третья — часть системы, экран для роли «Руководство» из [`../design/screens.md`](../design/screens.md).

## 10. Что должно быть видно в первый день эксплуатации

Минимум, без которого запускаться нельзя:

- p95 времени ответа по каждому маршруту
- Число заявок по статусам
- Заявки с нарушенным SLA
- Состояние всех 12 интеграций
- Размер DLQ
- Задержка доставки событий в «Raqamli nazorat»
- Все сработавшие риск-индикаторы
- Доступность за сутки

Остальное можно добавлять по мере надобности. Без этого списка запуск — это работа вслепую.
