# Инфраструктура и развёртывание

Где что крутится, как собирается и как восстанавливается. Схема развёртывания — [`diagrams.md`](diagrams.md), схема 4.

---

## 1. Окружения

| Окружение | Назначение | Данные | Кто разворачивает |
|---|---|---|---|
| **local** | Разработка на машине | Синтетические | Каждый сам, `docker compose up` |
| **dev** | Общая ветка, автодеплой | Синтетические | CI из `main` |
| **stage** | Опытная эксплуатация, приёмка | Обезличенная копия прода | CI по тегу |
| **prod** | Продуктив | Боевые | Вручную по тегу |

**Требование ТЗ (п. 6.2):** проверка и испытания проводятся на объектах Заказчика. Достаточным считается стенд из одного сервера, двух рабочих станций и локальной сети. То есть `stage` может быть скромным — это не полная копия прода.

`stage` нужен для опытной эксплуатации длительностью от 5 до 15 рабочих дней (п. 6.1) — этап 8.2 плана.

## 2. Состав продуктивного развёртывания

### Процессы

| Процесс | Образ | Команда |
|---|---|---|
| `frontend` | `ruxsatnoma-frontend` | `next start` |
| `core-api` | `ruxsatnoma-core` | `uvicorn core.api.main:app` |
| `core-worker` | `ruxsatnoma-core` | `python -m core.worker` |
| `integration-api` | `ruxsatnoma-integration` | `uvicorn integration.api.main:app` |
| `integration-worker` | `ruxsatnoma-integration` | `python -m integration.worker` |

Пять процессов из трёх образов. `api` и `worker` отличаются только командой запуска — общий код, разный вход.

### Инфраструктурные компоненты

| Компонент | Версия | Назначение |
|---|---|---|
| nginx | 1.24+ | Два vhost, TLS, маршрутизация, rate limit |
| PostgreSQL | 18 | Две базы: `ruxsatnoma_core` и `ruxsatnoma_integration` |
| PostGIS | 3.6 | Расширение для `core` |
| Redis | 7 | Сессии, кэш, rate limit, OTP |
| RabbitMQ | 3 | Очереди событий и уведомлений |
| MinIO | последняя | PDF/A, фото, видео |

### Требования ТЗ к оборудованию

Из п. 4.3.5, минимум:

| Сервер | Требования |
|---|---|
| Приложений | 8 ядер от 2,4 ГГц, 32 ГБ ОЗУ с расширением до 64, 500 ГБ SSD, канал 100 Мбит/с |
| Базы данных | 8 ядер от 3,0 ГГц, 32 ГБ ОЗУ, **5 ТБ SSD в RAID**, канал 100 Мбит/с |
| Файловый и объектный | 10 ТБ с расширением, checksum и versioning |
| Резервных копий | Двукратный объём основного хранилища |
| Общее | Мониторинг, журнал событий, удалённое управление, **ОС семейства Linux** |

Расчёт из ТЗ: до 30 МБ данных на разрешение, до 30 000 разрешений в год — около 0,9 ТБ в год, 4,5 ТБ за пять лет. Оборудование должно иметь запас на **5 лет без обновления**.

ЦОД организуется по **ВМҚ 107-сон** от 14.03.2023. Вопрос **О1** закрыт 10 августа 2026:

| Что | Ответ |
|---|---|
| Площадка | Имеется; конкретная для проектирования значения не имеет |
| Ресурсы | Виртуальные машины |
| Оркестрация | **Kubernetes не используется.** Docker Compose на виртуальных машинах |
| Резервная площадка | Имеется |
| Периметр — межсетевой экран, WAF, DDoS | Отвечает технический лидер Исполнителя |

Отказ от Kubernetes означает, что схема развёртывания в промышленной среде повторяет локальную: те же образы, тот же `docker compose`, отличия только в конфигурации и секретах.

## 3. Конфигурация nginx

Два `server`-блока. Между ними нет общей конфигурации — это принципиально.

### Публичный vhost

```nginx
server {
    listen 443 ssl http2;
    server_name ruxsatnoma-urmon.uz;

    client_max_body_size 50m;
    add_header X-Request-Id $request_id always;

    limit_req_zone $binary_remote_addr zone=api:10m rate=300r/m;
    limit_req_zone $binary_remote_addr zone=public:10m rate=30r/m;

    location /api/      { limit_req zone=api burst=50;    proxy_pass http://core-api; }
    location /public/   { limit_req zone=public burst=10; proxy_pass http://core-api; }
    location /webhooks/ { proxy_pass http://integration-api; }
    location /bff/      { proxy_pass http://integration-api; }
    location /          { proxy_pass http://frontend; }
}
```

### Закрытый vhost для ИМУТ

```nginx
server {
    listen 443 ssl http2;
    server_name nazorat.ruxsatnoma-urmon.uz;

    # IMUT network only
    allow 10.0.0.0/8;
    deny all;

    # read-only: reject any mutating method
    if ($request_method !~ ^(GET|HEAD|OPTIONS)$) { return 403; }

    location /api/v1/oversight/ { proxy_pass http://core-api; }
    location /                  { proxy_pass http://frontend; }
}
```

Диапазон адресов ИМУТ — заполняется по ответу на вопрос **Б3**.

Проверка метода на уровне nginx — четвёртый рубеж защиты после интерфейса, API и СУБД. Дублирование намеренное.

### Заголовки безопасности

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options nosniff always;
add_header X-Frame-Options DENY always;
add_header Referrer-Policy strict-origin-when-cross-origin always;
add_header Content-Security-Policy "default-src 'self'; connect-src 'self' wss://127.0.0.1:64443 wss://127.0.0.1:64646; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; font-src 'self' data:" always;
```

Порты `64443` и `64646` в CSP — локальный websocket E-IMZO. Без них подпись в браузере не работает; это подтверждается конфигурацией действующей платформы.

`X-Frame-Options: DENY` — в отличие от старой системы, где стоит `ALLOWALL`.

## 4. Сборка образов

Многоступенчатая сборка, непривилегированный пользователь, только необходимое в финальном слое.

```dockerfile
FROM python:3.13-slim AS builder
WORKDIR /build
COPY pyproject.toml uv.lock ./
RUN pip install --no-cache-dir uv && uv sync --frozen --no-dev

FROM python:3.13-slim
RUN useradd --create-home --shell /bin/false app
WORKDIR /app
COPY --from=builder /build/.venv /app/.venv
COPY --chown=app:app core/ ./core/
USER app
ENV PATH="/app/.venv/bin:$PATH"
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"
EXPOSE 8000
CMD ["uvicorn", "core.api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Образ фронтенда — стандартный многоступенчатый Next.js со `standalone`-сборкой.

## 5. CI и CD

### Конвейер на каждый пуш

| Шаг | Инструмент |
|---|---|
| 1 | `ruff check` и `ruff format --check` |
| 2 | `mypy` в строгом режиме |
| 3 | `lint-imports` — границы модулей |
| 4 | `check_english_only.py` |
| 5 | `pytest` — модульные и интеграционные |
| 6 | Схема БД накатывается на чистую базу |
| 7 | Проверка пяти критичных ограничений |
| 8 | `bandit` и `pip-audit` |
| 9 | Сборка образов |

Ни один шаг не пропускается. Красный CI — код не вливается.

### Развёртывание

| Окружение | Триггер | Способ |
|---|---|---|
| `dev` | Слияние в `main` | Автоматически |
| `stage` | Тег `v*.*.*-rc*` | Автоматически |
| `prod` | Тег `v*.*.*` | **Вручную, с подтверждением** |

Порядок выката: миграции → `core-api` → `core-worker` → `integration-*` → `frontend`.

**Миграции обратимы.** Каждая имеет `downgrade`, проверенный на `stage`. Миграции данных и структуры — разными файлами, чтобы откат структуры не терял данные.

## 6. Секреты

Не в репозитории, не в образах, не в переменных docker-compose с реальными значениями.

| Что | Где хранится |
|---|---|
| Пароли БД, брокера, MinIO | Хранилище секретов ЦОД |
| Сертификаты mTLS для ИМУТ | То же, монтируются в контейнер |
| Ключи платёжных провайдеров | То же, в БД только ссылка `vault://...` |
| Секрет подписи JWT | То же, ротация раз в квартал |

В репозитории — только `.env.example` с пустыми значениями. В `.gitignore` закрыты `.env`, дампы БД и `migration/dumps/` — в дампе старой системы персональные данные.

## 7. Резервирование и восстановление

Требования: **RPO ≤ 15 минут, RTO ≤ 4 часа**, доступность ≥ 99,7 %.

| Механизм | Периодичность | Хранение |
|---|---|---|
| Архивация WAL | Непрерывно | 30 дней |
| Полная копия | Еженедельно | 3 месяца |
| Инкрементальная | Ежедневно | 30 дней |
| Копия MinIO | Ежедневно | 30 дней |
| Потоковая репликация | Непрерывно | Резервная площадка |

RPO ≤ 15 минут обеспечивается **только непрерывной архивацией WAL**. Требование п. 4.3.2.4 о копии раз в две недели ему противоречит — берём строгий вариант, это расхождение **Р2**.

### Проверка восстановления

Плановая, с протоколом — требование сценария С24. Раз в квартал: развернуть копию на отдельном стенде, проверить целостность, зафиксировать время восстановления. Непроверенная резервная копия резервной копией не является.

### Порядок при отказе основной площадки

1. Переключение DNS на резервную площадку
2. Повышение реплики до основной
3. Проверка целостности последних транзакций по WAL
4. Запуск процессов приложения
5. Проверка очередей: недоставленные события в outbox

Целевое время — 4 часа. Порядок должен быть отработан, а не описан: сценарий С24 требует планового тестирования.

## 8. Режимы работы

Из п. 4.1.1.3 ТЗ, четыре режима.

| Режим | Когда | Поведение |
|---|---|---|
| **Нормальный** | Штатно | 24/7/365 |
| **Ограниченный** | Недоступен внешний сервис | Основные функции работают, запросы в outbox, retry, пользователю объясняется ситуация, при необходимости бумажный документ и maker-checker |
| **Аварийный** | Отказ компонента | Безопасная остановка с сохранением данных, отключение периферии, создание копии |
| **Восстановление** | Отказ основного ЦОД | Работа на резервной площадке |

Поведение в ограниченном режиме по каждому сервису — [`diagrams.md`](diagrams.md), схема 12.

### Критерии отказа и время восстановления

| Функция | Восстановление |
|---|---|
| Аудит и журналирование | **1 час — критично** |
| Приём заявок, GIS, платежи, разрешения, надзор | 4 часа |
| Инспектор, отчёты, интеграции | 8 часов |

Аудит восстанавливается первым: без него нельзя доказать, что происходило во время сбоя.

## 9. Масштабирование

При 30 000 разрешений в год и 1000 одновременных пользователей вертикального масштабирования достаточно на весь срок.

Требование п. 4.1.4: замедление при росте объёма данных устраняется наращиванием мощности сервера и каналов **без изменений в системе**. То есть архитектура не должна упираться в код.

Что заложено на случай роста:

| Компонент | Как масштабируется |
|---|---|
| `core-api`, `integration-api` | Горизонтально, состояния в процессе нет |
| `core-worker` | Горизонтально, задания через очередь |
| PostgreSQL | Вертикально, затем реплики только на чтение |
| Redis, RabbitMQ, MinIO | Вертикально, при необходимости кластер |

Запас ресурсов — **не менее 20 %** сверх максимальной нагрузки, требование п. 4.1.5.
